Host, measured in the same command as the measurement: **Linux**, Fedora Linux 45 (Forty Five), kernel
`7.2.15-300.fc45.x86_64`, node **v24.22.1**, `git version 2.56.0`. Store: `./selfdev.sqlite`. Probe:
`.spike/delegate/usage-census.mjs ./selfdev.sqlite` (1.1 s, read-only, no broker, no key, no model). Raw output:
`docs/evidence/2026-11-09-milestone-m5/cache-census-2026-11-09.txt`.

## 1. The ledger is the wrong instrument, and the record has been reading it

`./selfdev.sqlite.spend.jsonl` reports **`cached_tokens: 0` on all 2,030 rows**. That is not the rig's cache
behaviour; it is the ledger's scope. `src/providers/spend.mjs` writes a ledger row only when
`isMeteredModel(...)` / `endpointClass(...) === "metered"`, so every loopback call — most of the rig's traffic —
never reaches the ledger. Any conclusion about prompt caching drawn from that file is measuring an empty table.

## 4. What this decides

1. **A dynamic prompt section paid for by the verifier is paid in full every call.** The verifier's family has
   no cache to invalidate because it has no cache to hit. ROADMAP 175's gate therefore reads: dynamic sections
   are cheap on the seat arm (88–99% of prompt tokens are already cache reads) and expensive on the verifier arm.
   The two arms need different section policies, not one policy.
2. **`cacheWrite` is 0 everywhere.** Nothing on this rig is being *written* to cache as a separately billed
   event; the cache-read share comes from prefix reuse inside the serving stack. So the design question is not
   "how much does cache write cost" but "how much of the prompt is fresh each turn" — and the answer for the
   seat arm is ~1.7% of prompt tokens.
3. **A static-invariants section (ROADMAP 163) is nearly free on the seat arm and full-price on the verifier.**
   That asymmetry is the measurement the memory plan's §7 gate was missing.
4. **Conversation→seat mapping is not exposed.** The census keys by conversation id; per-seat attribution needs a
   cheap mapping. That is the gap ROADMAP 349's prescription (1) names.

## 5. What is *not* claimed

No invoice reconciliation: the token counts come from provider responses the harness recorded, not from a bill.
`cacheWrite: 0` may mean the provider reports it differently rather than that nothing was written. The probe
counts entries whose record contains `"usage"`; a row-scoped query would be needed to attribute a specific turn
to a specific seat, which is the mapping gap above.
