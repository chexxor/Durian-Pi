+// demo/lease-monitor.test.mjs — the priority lease is MONITORED, not just logged (#7114, N35 / D266).
+//
+// THE DEFECT this closes: `set_priority` writes a lease, `effectivePriority` honours it, `queueItemLine`
+// prints it on the row — and NOTHING counts it. A reordering mechanism with no counter drifts silently:
+// leases that never expire, rows whose lease lapsed but whose stored value still reads urgent to any reader
+// that reads the raw field, and rows carrying a level the vocabulary does not contain. #2643's rule is that
+// a mechanism must be monitored, not merely logged; D266 registered this as the read-surface gap.
+//
+// THE CONTRACT this pins:
+//   1. Every read reports THREE numbers: live leases, lapsed-but-stored leases, invalid leases.
+//   2. The numbers CHANGE at the instant a lease crosses its `expiresAt` — that is the falsifier. A count
+//      that cannot move is a description, not a monitor.
+//   3. A lapsed lease is INERT in ordering. "Stored and inert" is correct; "stored and acting" is the bug,
+//      and the row's `acting` field is what makes the two distinguishable.
+//   4. A malformed lease (unknown level, missing/unparseable expiry, no reason) is counted and named by
+//      reason, never silently coerced to neutral.
+//   5. The readout names, per seat, the RESOLVED claim strategy and its SOURCE (seat | team | default),
+//      because a lease is inert on a seat that claims `oldest_first` — a fleet cannot monitor a mechanism it
+//      cannot tell which seats have enabled.
+//   6. A rig with no leases renders the queue header EXACTLY as before: the monitor adds no noise to a rig
+//      that has never used the mechanism (the same convention as the strategy footer in src/watchview.mjs).

+# The priority lease: counted, not assumed
+
+## When to use
+A `set_priority` was issued and the seat's claim order did not change; or you need the fleet number for the
+mechanism — how many leases are LIVE, how many have LAPSED but are still stored, how many are INVALID. A
+reordering mechanism that is only logged drifts silently (#2643): 50 live leases on a rig where no seat
+honours priority is a pile of stored fields, not a policy.
+
+## Impact
+Two distinct failures get confused. (1) The lease is REAL but the recipient claims `oldest_first`, so the
+lease is recorded and inert — the seat never looks at priority. (2) The lease has passed its `expiresAt`, so
+it is stored history, not policy; if some reader still acts on the stored value, that is the
+"stored-and-acting" bug. Neither is visible without a count, and both read as "the queue order is random".
+
+## Preconditions
+Read-only. No broker stop, no write. A resident broker answers reads with the code it started with, so an
+older broker serves a census without the `leases` block; the CLI then derives it locally from the rows it
+already holds (the same skew fallback as `workStrategy`).
+
+## Diagnose (read-only)
+```bash
+DURIG_DB=./selfdev.sqlite node cli.mjs status
+DURIG_DB=./selfdev.sqlite node cli.mjs queue --status queued --no-body
+```
+Read `leases` in the payload:
+
+```
+leases: 50 live, 0 lapsed-but-stored, 0 invalid | (7213 rows read) |
+claim order: team priority_first(team); impl=priority_first(seat), qa=priority_first(team), ...
+```
+Measured on this rig 2026-11-12 with those exact commands: 7,213 rows read, 50 live leases, 0 lapsed, 0
+invalid, 0 live leases sitting on a seat that ignores them. The per-seat strategy is reported with its
+SOURCE (`seat` | `team` | `default`) — that is what reconciles "the operator said the team stays
+`oldest_first`" with what the rig file actually declares: `rig.selfdev.json` line 4 says
+`"workStrategy": "priority_first"`, so a seat reporting `priority_first (from team)` is correct and the note
+is stale. Check the file, not the note.
+
+A seat sees the same numbers on its own read: `peek_queue`'s header carries
+`| leases: N live, M lapsed-but-stored, K invalid; <seat> claims by <strategy> (from <source>)` — printed only
+when there is something to count, so a rig that never used the mechanism renders unchanged.
+
+## Do
+1. If `unorderedLive > 0`: the leases are on seats that claim `oldest_first`. Either set the seat (or the
+   team) to `priority_first` with `up <rigfile> --refresh` (broker stopped — `up` refuses while it drives),
+   or accept that the leases are inert and let them lapse.
+2. If `lapsed` keeps growing and nothing is re-leased: the mechanism is being used once and never renewed.
+   `set_priority` requires an expiry at most 30 days out, so a lapsed lease is the system working as
+   designed — it is the count telling you nobody is paying attention.
+3. If `invalid > 0`: a row carries a level outside `now|next|later`, a missing/unparseable `expiresAt`, or no
+   reason. `set_priority` refuses all of those, so an invalid row means it was hand-edited into the store or
+   predates the writer. Find it by id in `leases.invalidIds` and fix the row or cancel it.
+
+## Verify
+```bash
+node demo/lease-monitor.test.mjs
+```
+Expect `LEASE MONITOR PASS`, exit 0. The demo asserts TRANSITIONS, not existence: a lease crossing its
+`expiresAt` moves from live to lapsed and the claim order falls back to id order, and a poisoned row
+(`priority: "urgent"`) appears in the invalid count with `unknown-level` named.
+
+## If it fails
+If `leases` is absent from the payload entirely, the serving broker predates the monitor — re-read with
+`--local` or restart the broker from this tree (docs/runbooks/broker-safe-change.md). The monitor never
+throws: a malformed row is counted, never coerced.
+

+`pm` for queue ordering policy; `lead` if a live lease is being ignored by a seat that claims
+`priority_first`.

+// src/leasemonitor.mjs — the MONITORED artifact for the priority lease (#7114, ROADMAP N35 / D266).
+//
+// WHY THIS EXISTS. `set_priority` writes a lease, `effectivePriority` honours it at read time, and
+// `queueItemLine` prints it on a row the seat is looking at. None of that is a MEASURE. #2643's rule is
+// that a mechanism must be MONITORED, not merely logged: without a count, a rig can accumulate leases that
+// never expire, rows whose lease lapsed but whose stored value still reads urgent to some other reader, and
+// hand-edited rows carrying a level the vocabulary does not contain — and every read still says "ok". A
+// reordering mechanism with no counter drifts silently, and the drift is invisible precisely because the row
+// looks normal (the same pathology `hold` measured: 197 parked rows, median 564.9 h).
+//
+// WHY THREE NUMBERS AND NOT ONE. "Leased" and "lapsed" are different failures. A LIVE lease is intended
+// behaviour. A LAPSED lease is stored-and-inert — correct, and worth counting only so a reader can tell
+// "the mechanism is working" from "the mechanism is accumulating dead weight". An INVALID row is the bug:
+// a level outside `now|next|later`, an unparseable or missing `expiresAt`, or a lease with no reason. Those
+// are rows the writer refused to create, so their presence means something bypassed the writer.
+//
+// THE ONE THISS MONITORS THAT A COUNT ALONE CANNOT: a lapsed lease is only inert if the ordering code reads
+// the EFFECTIVE value. `effectivePriority` is the single place that decides what a row's priority means
+// right now, and no ordering path reads `item.priority` raw (checked across src/, cli.mjs). This module
+// therefore reports, per row, both the stored value and the value the selector actually uses, so a reader
+// can see the two agree rather than trust that they do.
+//
+// Pure functions over plain row objects, no I/O and no clock captured at import — `now` is injected, so the
+// transition "a lease crosses its expiresAt" is assertable in a demo without waiting for time to pass.
+
+import {
+	DEFAULT_STRATEGY,
+	NEUTRAL_PRIORITY,
+	PRIORITY_RANK,
+	effectivePriority,
+	resolveStrategy,
+} from "./workstrategy.mjs";
+
+/** Every reason a row can be counted INVALID, in the order a readout lists them. */
+export const LEASE_INVALID_REASONS = Object.freeze([
+	"unknown-level", // priority not in `now|next|later`
+	"missing-expiresAt", // a priority with no lease at all — `set_priority` always writes one
+	"unparseable-expiresAt", // a lease whose instant cannot be read
+	"missing-reason", // a lease nobody can explain (#6112's argument, applied to ordering)
+]);
+
+/**
+ * Classify ONE row's lease. Returns a small structured record rather than a boolean, because the readout has
+ * to say WHICH row and WHY, not just how many.
+ *
+ * `kind` is one of:
+ *   none    - the row carries no priority at all (the overwhelming majority; nothing to monitor)
+ *   live    - a valid level with a lease that has not yet passed
+ *   lapsed  - a valid level whose stored lease has passed: stored, inert
+ *   invalid - malformed in one of the LEASE_INVALID_REASONS ways
+ *
+ * `acting` is the load-bearing field: the priority the SELECTOR sees right now. A lapsed lease or an
+ * unknown level ranks neutral, so `acting` is null. A priority with NO lease (which `set_priority` cannot
+ * produce, so it means a hand-edited or pre-lease row) ACTS forever — the unbounded park the lease was
+ * invented to prevent — and it is counted INVALID precisely so that acting-forever is visible rather than
+ * assumed. If a LAPSED row ever shows a non-neutral `acting`, the ordering path is reading the stored value:
+ * that is the "stored-and-acting" bug this monitor exists to catch.
+ *
+ * @param {object} item a queue row
+ * @param {number} [now] epoch ms
+ */
+export function classifyLease(item, now = Date.now()) {
+	const raw = item?.priority ?? null;
+	if (raw === null || raw === undefined) return { kind: "none", id: item?.id, raw: null };
+
+	const eff = effectivePriority(item, now);
+	const expiresAt = item?.prioritySet?.expiresAt ?? null;
+	const knownLevel = typeof raw === "string" && Object.hasOwn(PRIORITY_RANK, raw);
+
+	const reasons = [];
+	if (!knownLevel) reasons.push("unknown-level");
+	if (expiresAt === null || expiresAt === undefined) reasons.push("missing-expiresAt");
+	else if (!Number.isFinite(Date.parse(String(expiresAt)))) reasons.push("unparseable-expiresAt");
+	const reason = item?.prioritySet?.reason;
+	if (!(typeof reason === "string" && reason.trim() !== "")) reasons.push("missing-reason");
+
+	const level = knownLevel ? raw : null;
+	// What the selector ACTUALLY uses, taken from the same function the selector calls. Reporting an ideal
+	// instead of the real value would make the monitor a claim rather than a measurement.
+	const acting = eff.priority === NEUTRAL_PRIORITY ? null : eff.priority;
+	const kind = reasons.length > 0 ? "invalid" : eff.lapsed ? "lapsed" : "live";
+
+	return {
+		id: item?.id,
+		to: item?.to ?? null,
+		status: item?.status ?? null,
+		kind,
+		raw,
+		level,
+		acting,
+		expiresAt,
+		lapsed: eff.lapsed,
+		lapsedAt: kind === "lapsed" ? expiresAt : null,
+		reasons,
+		by: item?.prioritySet?.by ?? null,
+		authority: item?.prioritySet?.authority ?? null,
+	};
+}
+
+/**
+ * THE THREE NUMBERS, per read. `leased`, `lapsed` and `invalid` are counts over the rows handed in; `rows`
+ * is how many rows were looked at, so a count of 12 leased out of 12 read is not confused with 12 out of
+ * 6,000. `detail` carries only rows that carry a priority — a full row list for 7,000 rows would be a payload,
+ * not a monitor.
+ *
+ * `actingUnder` names the strategy the counts were computed against: a lease is inert on a seat whose
+ * resolved strategy is not `priority_first`, so the same store can legitimately show 0 reordered rows and
+ * 12 live leases. Reporting the two together is what makes the number interpretable instead of alarming.
+ *
+ * @param {Array<object>} items queue rows
+ * @param {{now?: number, strategyView?: {team: {strategy: string, source: string}, seats: Record<string, {strategy: string, source: string}>}}|null} [opts]
+ *
+ * NOTE ON DETERMINISM: the report carries NO wall-clock stamp of its own. `demo/queue-compat-args.test.mjs`
+ * pins that two reads of the same store produce identical bytes, and a `readAt: <now>` field would break that
+ * pin for a reason that has nothing to do with the queue. What is knowable is stored: every lease's own
+ * `expiresAt` is in the row, so "when did it lapse" is answerable from the data, not from the moment of reading.
+ */
+export function leaseReport(items, { now = Date.now(), strategyView = null } = {}) {
+	const rows = items ?? [];
+	const detail = [];
+	for (const item of rows) {
+	 const c = classifyLease(item, now);
+		if (c.kind !== "none") detail.push(c);
+	}
+	const live = detail.filter((c) => c.kind === "live");
+	const lapsed = detail.filter((c) => c.kind === "lapsed");
+	const invalid = detail.filter((c) => c.kind === "invalid");
+
+	const seatOrders = strategyView?.seats ?? {};
+	const team = strategyView?.team ?? { strategy: DEFAULT_STRATEGY, source: "default" };
+
+	// A row is only ORDERED by its lease if the seat it is addressed to honours priority. Counting a live
+	// lease as "moving the queue" when the recipient claims oldest-first is the false green this avoids.
+	const ordered = live.filter((c) => {
+		const resolved = seatOrders[c.to] ?? team;
+		return resolved.strategy === "priority_first";
+	});
+
+	return {
+		rows: rows.length,
+		leased: live.length,
+		lapsed: lapsed.length,
+		invalid: invalid.length,
+		unorderedLive: live.length - ordered.length,
+		earliestExpiry: live.reduce((acc, c) => (acc && Date.parse(c.expiresAt) < Date.parse(acc) ? c.expiresAt : acc), null),
+		reasonCounts: invalid.reduce((acc, c) => {
+			for (const r of c.reasons) acc[r] = (acc[r] ?? 0) + 1;
+			return acc;
+		}, {}),
+		// The rows a priority-first seat will actually look at first, so a reader can check the count against
+		// the order rather than take it on faith.
+		orderedLive: ordered.map((c) => c.id),
+		lapsedIds: lapsed.map((c) => c.id),
+		invalidIds: invalid.map((c) => c.id),
+		// Bounded on purpose: 7,000 rows can hold a lot of bad leases, and a monitor that dumps them all is a
+		// payload. The counts above are the full set; this is the first page of evidence.
+		detail: detail.slice(0, 40),
+		detailTruncated: detail.length > 40,
+		strategy: strategyView ? { team, seats: seatOrders } : null,
+	};
+}
+
+/**
+ * Render the monitor for a human, one line: the three numbers, then who is actually honouring them.
+ * `strategyView` comes from `workStrategyView` (src/readapi.mjs) — the same derivation `status` and `ps`
+ * print — so the line cannot disagree with the strategy readout the operator already trusts.
+ */
+export function renderLeaseLine(report) {
+	if (!report) return "leases: no report";
+	const parts = [
+		`leases: ${report.leased} live, ${report.lapsed} lapsed-but-stored, ${report.invalid} invalid`,
+		`(${report.rows} rows read)`,
+	];
+	if (report.unorderedLive > 0)
