# pi-multi-agent vs durig — competitor comparison

**Date:** 2026-10-12 · **Read at:** `vendor/eval/pi-multi-agent` HEAD `d2fef0f`
("docs: rewrite README with execution modes, model routing, and workflow engine",
2026-06-07) · **Licence:** MIT (`LICENSE`) · **Version:** `package.json` `1.0.0`.

**Repo:** https://github.com/jwangkun/Pi-Multi-Agent

**One-line:** a TypeScript **orchestration library + Express/WebSocket server +
Next.js dashboard** that runs a swarm of LLM sub-agents (plan → cluster →
evaluate → replan) with multi-model routing and a generated-JS workflow engine.

**Category note — it is not the same thing as us.** Despite the "Pi" in the name
it is unrelated to the `@earendil-works/pi` coding agent; it is a standalone
framework that calls OpenAI-compatible chat completions directly
(`OpenAI` client, default `https://api.deepseek.com`, `src/orchestration/*.ts`).
It has **no durable queue, no seat/pod topology, no skills system, and no
grounding/citation discipline.** So it does not compete with durig's substrate;
it is worth reading as a **feature and design comparator** — several of its
mechanisms are ones we should consciously match or beat.

---

## 1. Feature / consideration matrix

Legend: **● ours** (durig has it) · **◐ partial** · **○ absent there**.

| Concern | pi-multi-agent | durig |
|---|---|---|
| **Durable work queue (claim/block/handoff + transition audit)** | ○ — tasks are in-memory `Map`s (`AgentCluster.progress`, `results`; `src/orchestration/agent-cluster.ts`); only the *final session snapshot* is written (`server/session-store.ts`) | ● typed queue items with append-only transitions |
| **Seat/pod topology** | ○ — "agents" are per-goal LLM roles generated by the planner (`DeepPlanner.createDeepPlan`, `src/orchestration/deep-planner.ts`); no persistent named seats | ● declared rig/pod/seat spec |
| **Skills system** | ○ — **zero** occurrences of "skill" anywhere in the repo (grep over `*.ts`/`*.tsx`/`*.md`). Reusable role behaviour lives in hard-coded prompt strings (`src/tools/agent-as-tool.ts` `agentPrompts`) | ● agentskills.io-style skills projected per seat |
| **Role instructions** | ◐ — `assignedAgentPrompt` generated per sub-task by the planner, not a versioned role artifact | ● `guidance/role.md` per seat |
| **Multi-model routing** | ● — 5 strategies: complexity / tool-aware / specialty-match / cost-optimized / direct (`ModelRouter`, `src/models/router.ts`; README "Routing Strategies"). This is **ahead of us** | ◐ one model per seat (pi + DeepInfra) |
| **Plan → execute → evaluate → replan loop** | ● — 4-dimension LLM evaluation (accuracy/completeness/consistency/format) with threshold + retry (`DeepEvaluator`, `src/orchestration/deep-evaluator.ts`; loop in `AgentCluster.executePlan`) | ◐ QA re-run / pair review, but no scored quality gate |
| **Clarify-before-execute** | ● — `/api/clarify` returns `WAITING_INPUT` + a `uiSchema` form for genuinely ambiguous tasks (`server/index.ts:457`) | ◐ "ask for the missing decision" is a norm, not a structured gate |
| **Structured output (JSON-schema validated)** | ● — `parseStructuredOutput` + schema fail-fast per agent (`src/workflow/runtime.ts`, `src/workflow/structured-output.ts`) | ◐ |
| **Generated-JS workflow engine** | ● — LLM writes a JS script using `agent()/parallel()/pipeline()/phase()/log()`, run in `vm` (`src/workflow/workflow.ts`, `src/workflow/runtime.ts`) | ◐ our skills/workflows are agent-driven, not a deterministic script VM |
| **Token budget / concurrency cap** | ● — `TokenBudget` (`src/workflow/budget.ts`), `maxConcurrentAgents` queue (`drainQueue`, `runtime.ts`) | ◐ context-pressure guarding |
| **Crash/restart recovery** | ◐ — atomic per-session JSON snapshot (`writeSnapshot` uses tmp+rename) + stale-`running` expiry (`expireStaleRunningSessions`); **in-flight cluster state is lost** | ● durable resume/restart of seats and queue |
| **Cross-seat observation** | ● — WebSocket live event stream + dashboard (`ClusterEvent` types; `web/src/app/page.tsx`) | ● `rig capture` + queue |
| **Human escalation** | ◐ — clarify form only; no approval gate on tool calls | ● queue `block` + human escalation |
| **Grounding / citations** | ○ — no retrieval; the "knowledge_base" and "data_analyzer" tools return **canned template text** (`src/tools/index.ts`) | ● every claim cites a page/section |
| **Security model** | ○ — see §4; open CORS, no auth, `vm` mis-sold as a sandbox | ● security consult + guard rails |
| **Native Windows** | ◐ — Node/TS is cross-platform; no Windows-specific work or claim | ● native Windows (hard requirement) |

**Honest read:** on *orchestration mechanics* (routing, quality gate, structured
workflow, clarify gate) this project is genuinely ahead in a few places. On
*everything that makes a grounded rig trustworthy* (grounding, durability, skills,
security) it is far behind — largely because it is solving a different problem
(research-report generation, not a grounded domain).

## 2. Skills — the direct answer

There is **no skills concept**: no skill files, no loader, no registry, no
progressive disclosure. Reusable behaviour is prompt text baked into
`agentPrompts` (`src/tools/agent-as-tool.ts`) and the planner's
`assignedAgentPrompt`. Our skills projection, `guidance/role.md`, and the
pair-review/reviewer norms are strictly ahead of this project and we should not
copy anything here.

## 3. Workflows — worth studying

The workflow engine is the most interesting mechanism:

- An LLM generates a JS script from the task (`WORKFLOW_SYSTEM_PROMPT`,
  `src/workflow/workflow.ts`) with a literal `meta` block, then `phase()`,
  `agent()`, `parallel()`, `pipeline()`, `log()`, `args`, `cwd`, `budget`
  globals (`src/workflow/runtime.ts`).
- It runs under `vm.createContext` with a curated global whitelist and a
  300 s script timeout; outputs can be JSON-schema validated; token budget and
  concurrency are enforced.
- **The API is essentially the same as `pi-extensible-workflows-vekexasia`,
  which we already vendored** (`vendor/eval/pi-extensible-workflows-vekexasia`:
  `agent()` / `parallel()` / `pipeline()` / `phase()`). This project **does not
  cite it** — worth noting as a shared design lineage, not a differentiator.

Lesson for us: a deterministic, budgeted script layer over agent calls is a real
capability we do not have; it is on the table if we ever want reproducible
multi-agent pipelines rather than seat-driven work.

## 4. Sources they cite / "researched"

- The repo contains **only three markdown docs** (`README.md`, `CONTRIBUTING.md`,
  `CODE_OF_CONDUCT.md`) and **no prior-art or citation section**.
- Every external URL in source is a provider API or a search URL: DeepSeek
  (`https://api.deepseek.com`), OpenAI, Anthropic, DuckDuckGo Instant Answer
  (`https://api.duckduckgo.com/`), and Google search
  (`https://www.google.com/search?q=`, also used as a *fabricated* fallback
  result snippet in `src/tools/index.ts`).
- The "web_search" tool queries the **DuckDuckGo Instant Answer API** (not a
  results API) and, on empty/failed responses, returns a search *URL* with
  model-authored snippet text. The "knowledge_base" tool explicitly says it has
  no real data source. So their "research" grounding is largely a **stub** —
  the opposite of our retrieval-and-cite rule.

## 5. Security considerations (read before borrowing anything)

These are concrete and should gate any reuse:

1. **`vm` is not a security boundary.** Node's `vm` docs say so explicitly; the
   workflow engine and the README call it "sandboxed". An LLM composes the
   script that runs in that context — a prompt-injection → code-execution path.
2. **`code_executor` is arbitrary JS in-process.** `new Function('sandbox',
   'with(sandbox){...}')` (`src/tools/index.ts`) does not shadow `globalThis`/
   `process`; an empty `sandbox` blocks nothing.
3. **SSRF in `web_scraper`.** It `fetch`es any URL supplied by the model, with no
   allowlist/deny list (`src/tools/index.ts`) — internal metadata endpoints and
   localhost are reachable.
4. **No authentication, wide-open CORS.** `app.use(cors())` and the API has no
   auth/authz (`server/index.ts`); anyone who can reach the port can drive
   agents, read every session, and read the configured provider keys.
5. **Provider keys live in server config and are used server-side**
   (`buildModelRegistry`, `server/index.ts`). Not leaked to the dashboard in the
   paths inspected, but there is no secret-handling discipline.
6. **`calculator`** sanitises to `[0-9+\-*/.()%\s]` before `new Function` — the
   only place that is close to safe.

Given our team norm ("Seats MUST route any change touching network egress,
secret handling, untrusted-input/prompt-injection, or licensed-corpus handling
through `security.sec`"), nothing here should be lifted without a security
position first. The right use is **negative example**: it shows the failure mode
of shipping an "agent sandbox" that isn't one.

## 6. Reusable lessons worth considering (and where we already match)

| Their decision | Why it is interesting | Our counterpart |
|---|---|---|
| **Complexity-based model routing with 5 strategies** (`src/models/router.ts`) | Matches cost/capability to the sub-task instead of one model per seat | one model per seat — a concrete gap if cost/latency matters |
| **4-dimension scored quality gate with replan/retry** (`DeepEvaluator` + `executePlan` loop) | Turns "looks done" into a measurable pass/fail, not an opinion | QA re-run + pair review (behavioural, not scored) |
| **Clarify gate returning a structured form before execution** (`/api/clarify`) | Prevents building the wrong thing; names `WAITING_INPUT` explicitly | our norm to ask for the missing decision is not mechanised |
| **JSON-schema-validated structured output per agent** (`structured-output.ts`) | Machine-checkable handoffs between agents | free-text handoffs |
| **Deterministic, budgeted JS workflow over agent calls** (`runtime.ts`) | Reproducible pipelines + hard token ceiling | no script layer today |
| **Atomic session snapshot (tmp+rename) + stale-running expiry** (`session-store.ts`) | Cheap crash-safety for finished sessions | durable substrate is stronger, but the tmp+rename write is a good pattern |
| **Live WebSocket event stream for observation** (`ClusterEvent`, dashboard) | Cheap cross-agent visibility | `rig capture` + queue |

## 7. Verdict

- **Not a substrate competitor.** Different layer (library/server vs durable
  rig), no queue, no seats, no skills, no grounding, and a security posture we
  would reject. Do not switch to it or vendor it into the build.
- **Beat it where it wins.** The two genuinely ahead mechanisms are
  **multi-strategy model routing** and a **scored quality gate**; the clarify
  `uiSchema` gate and schema-validated handoffs are also worth a look.
- **Do not borrow its sandbox.** `vm`/`Function` "sandboxing" is the exact
  anti-pattern our security norm exists to prevent.
- Agent-fleet remains the deeper comparators entry;
  this project is recorded separately in `COMPETITORS.md`.
