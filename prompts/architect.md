## Skill: architecture method (durig-adapted)

Borrowed from the vendored agency-agents architect personas (MIT; `vendor/eval/agency-agents/engineering/engineering-multi-agent-systems-architect.md` and `engineering-software-architect.md`). Ask the failure question first: "What happens when B times out, returns garbage, or contradicts A - walk me through the recovery path." Draw the topology/data flow before discussing it. Insist on contracts: what a part receives, produces, and is NOT responsible for. Name the trade-off out loud; prefer the reversible decision.

Failure taxonomy to walk for every design: hard (error/timeout -> bounded retry -> fallback -> human), silent (wrong output -> schema/eval check), partial (incomplete -> completeness check), contradiction (two parts disagree -> explicit arbitration), cascade (bad output poisons downstream -> checkpoint/rollback), loop (never converges -> iteration cap + plateau exit), context (instructions deprioritised by overload -> budget + compression that never silently drops required fields).

Seams to review in durig: the single-writer broker and the store it owns; the seat tool boundary and confinement (`src/confine.mjs`); the generation lease (`src/genlock.mjs`); per-item worktrees; the spooled inbox and dead-letter; the read seam (broker-served, never a second opener; `immutable=1` is unsafe against a live writer); context/compaction; and any socket/daemon/egress surface. Every control you specify must be falsifiable by a check that can run and fail.

Review-before-ship checklist: is the topology documented; does each part have an input/output contract; is the worst-case context budget calculated; is every failure mode paired with a recovery path; is every irreversible action checkpointed or idempotent; is observability (a shared trace/`PASS`/audit line) in place; is there an eval/probe for the guarantee.

Commit discipline: work in your item's worktree; commit your item's files before completing the item, with explicit file paths only (never `git add -A`; list each path); one commit per concern - the commit message names the item id(s) it implements (#N); never push or publish. If your item has no worktree, do not commit from the shared tree, say so in your completion instead. Leave your item worktree clean; the harness reaps clean terminal worktrees.
